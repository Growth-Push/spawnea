# Desktop distribution

Spawnea is distributed as a desktop application through GitHub Releases. Users download an installer or portable artifact; Node.js, pnpm, and an npm installation are not required.

## Supported first-release artifacts

| Platform | Architecture | Artifact |
| --- | --- | --- |
| macOS | arm64 | DMG |
| macOS | x64 | DMG |
| Windows | x64 | NSIS EXE installer |
| Linux | x64 | AppImage |

Linux `.deb` packaging is deferred from the first release. The current `electron-builder.yml` intentionally configures only AppImage; this keeps the first packaging path small and is not evidence that Debian packaging has been verified.

Artifact names follow `Spawnea-<version>-<platform>-<architecture>.<extension>`. Each release also contains platform-specific `SHA256SUMS-<platform>-<architecture>.txt` files generated by the packaging jobs.

## Local packaging

Install dependencies and package for the current host without publishing:

```sh
pnpm install --frozen-lockfile
pnpm package:desktop:host
```

The application is built with `electron-vite`, native dependencies are rebuilt for the Electron ABI, and artifacts are written to the repository `release/` directory. The directory is ignored by Git.

To select a target explicitly when the host toolchain supports it:

```sh
pnpm license:notices
pnpm --filter @spawnea/desktop build
pnpm --filter @spawnea/desktop exec electron-builder --config electron-builder.yml --publish never --linux AppImage --x64
```

The packaged application stores SQLite data and other operational data under Electron's user-data directory at runtime. Repository-local databases, credentials, local configuration overrides, logs, tests, source maps, and development files are excluded from the package.

Every package includes Spawnea's `LICENSE` and a generated
`THIRD-PARTY-NOTICES.txt` under its resources directory. The supported package
scripts regenerate the notices from the locked production dependency graph
before `electron-builder` runs.

## Creating a release

1. Update `version` in `apps/desktop/package.json`. This is the authoritative packaged application version.
2. Verify the version with the local build and relevant checks.
3. Create and push an annotated tag in the form `v<major>.<minor>.<patch>`, for example `v0.1.0`.
4. GitHub Actions validates that the tag version exactly matches `apps/desktop/package.json`.
5. Native macOS, Windows, and Linux jobs install with the frozen lockfile, run the quality gates, package the application, and generate SHA-256 checksums.
6. The workflow creates a draft GitHub Release and attaches all successful artifacts.
7. A human reviewer checks the artifact list, checksums, installation behavior, and release notes before publishing the draft manually.

The workflow has read-only repository permissions by default. Only the final draft-release job receives `contents: write`, and the workflow is tag-only rather than pull-request triggered. No release credentials are exposed to pull requests or untrusted code.

## Installing a release

- macOS users download the DMG matching Apple Silicon (`arm64`) or Intel (`x64`), open it, and move Spawnea to Applications.
- Windows users download the x64 NSIS EXE and run the installer.
- Linux users download the x64 AppImage, make it executable, and launch it.

The first technical builds are unsigned and are not notarized. macOS, Windows, or Linux security controls may therefore show warnings. Signed and notarized releases are required before positioning Spawnea as broadly suitable for non-technical users.

Remote hosts still require no Spawnea installation. They need standard SSH access, `tmux`, and the configured agent command and dependencies managed by the user. Automatic updates, npm launchers, code signing, and notarization implementation are separate work.

The packaged MCP bridge is supported on macOS and Linux. Windows MCP control is
deferred until named-pipe transport is implemented.
